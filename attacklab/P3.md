# Memory Architecture and Stack Collision

## Stack Allocation in getbuf vs hexmatch
- In [P1.md](file:///Users/bradleyyeo/Documents/learn/csapp3e-brad/attacklab/P1.md), `getbuf` allocates 40 bytes on the stack (`0x5561dc78` to `0x5561dc9f`).
- When `getbuf` returns, `%rsp` is restored to `0x5561dca8`.
- Injected code jumps to `touch3`, which subsequently calls `hexmatch`.
- `hexmatch` decrements `%rsp` by 128 bytes (`add $0xffffffffffffff80, %rsp`), moving the stack pointer down into `0x5561dc00`.
- The stack frame of `hexmatch` and its local array `cbuf[110]` completely overlap the address range previously occupied by `getbuf` (`0x5561dc78` to `0x5561dc9f`).

## The Clashing Buffer Problem
- If the ASCII string payload is placed inside the 40-byte buffer alongside the injected instructions, `hexmatch`'s stack allocations will clobber that data before `strncmp` runs.

## The Safe Storage Zone
- Memory located at addresses higher than the saved return address (`>= 0x5561dca8`) belongs to caller frames (`test`).
- `touch3` and `hexmatch` only write to addresses lower than their own stack frames.
- Placing the ASCII string at address `0x5561dca8` prevents it from being corrupted.

# C String Representation and Byte Encoding

## ASCII Encoding
- C strings are sequential byte arrays terminated by a null byte (`0x00`).
- Unlike multi-byte integer values, string characters follow index order from left to right; byte endianness does not reverse them.
- Cookie value from [cookie.txt](file:///Users/bradleyyeo/Documents/learn/csapp3e-brad/attacklab/target1/cookie.txt): `0x59b997fa`.
- String literal: `"59b997fa"`.
- Corresponding hex bytes: `35 39 62 39 39 37 66 61 00` (9 bytes total).

# Step-by-Step Implementation Approach

## Step A: Author Injected Assembly (p3.s)
- Set `%rdi` to point to the address of the string (`0x5561dca8`).
- Push the entry address of `touch3` (`0x4018fa`) onto the stack.
- Return via `ret`.
- Assemble and disassemble to obtain bytecodes:
```bash
gcc -c p3.s
objdump -d p3.o
```

## Step B: Map Payload Offsets (p3.txt)
- Offset `0` to `N`: Bytecode generated from `p3.s`.
- Offset `N` to `39`: Padding bytes to fill the remainder of the 40-byte buffer.
- Offset `40` to `47`: Overwrite return address with buffer start (`0x5561dc78` in little-endian: `78 dc 61 55 00 00 00 00`).
- Offset `48` onwards: 9-byte null-terminated ASCII string, positioned at address `0x5561dca8`.

## Step C: Test the Exploit
- Feed payload through `hex2raw` to `ctarget`:
```bash
./target1/hex2raw < p3.txt | ./target1/ctarget -q
```
